Arquitectura y código

Base adecuada para una V1: frontend Next.js, API FastAPI, SQL parametrizado con psycopg, Argon2id y sesiones persistidas; migraciones 0001–0009; exclusión SQL de solapes, cerrojo de habitación al reservar/retirar, precios aceptados conservados, cargos correctivos por reverso y roles que ocultan documento del huésped. El navegador consume API_BASE_URL; Vercel configura proxy /api hacia Railway. Las otras verticales tienen bibliotecas de dominio probadas y pantallas cerradas; no constituyen productos operativos persistentes.

Brechas: el runtime SQL no coincide con la descripción de adaptador que dice delegar todas las reglas al dominio; reglas duplicadas pueden divergir. Empresa y establecimiento sintéticos siguen fijados, habitaciones sin tenant; no existe multiempresa general. Conexión por request sin pool explícito, consultas repetidas por habitación en oferta y sin presupuesto de carga medido. Migraciones al arrancar sin coordinación interproceso: ensayar arranque concurrente antes de escalar. Reducir acoplamiento de rutas/seguridad/SQL, manteniendo tests de contrato y dominio.

No se auditó vulnerabilidad de dependencias por CVE, ni se verificó compatibilidad PostgreSQL 16/17: README declara 16 desplegado y la spec exige 17. Python no tiene versiones fijadas; la instalación actual resolvió versiones nuevas y pasó solo los tests indicados. Guardar un lock y artefactos reproducibles.
